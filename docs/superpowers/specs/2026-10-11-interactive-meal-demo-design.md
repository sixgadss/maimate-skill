# 麦Mate：预算配餐交互演示与真实接入设计

状态：待用户审阅；未实施。日期：2026-10-11。

## 目标与范围

用户已同意沿三个方向推进：打通一个真实配餐场景、让无账号访客能体验、展示可复用能力。本轮聚焦单人、立即到店自取的预算配餐，共用现有推荐引擎；不扩展到多品牌、团餐、外送或交易。

核心任务：设定预算和“不喝含糖饮料”等本餐限制，得到一份带商品明细、完整价格和理由的组合。成功意味着用户能亲手修改条件、核对结果、识别数据来源；不以 Star 增长作为工程验收标准。

受众：日常选餐用户与试用项目的开发者。用途：选定预算内的一餐。调性：playful。视觉延续原创细金拱门的“麦之宝库”。

## 现有能力与已核实事实

- Runtime 已实现候选生成、硬约束、完整报价校验、有限排序、SQLite 偏好与 CLI。
- `McdMcpAdapter` 通过实际 `tools/list` 检查输入 schema；默认真实绑定未验证，因此不开放真实推荐。
- 本会话没有可调用的麦当劳连接器。官方文档页显示未登录；尚未进行真实账号调用。
- [官方接入指南](https://open.mcd.cn/mcp/doc)公开 `https://mcp.mcd.cn`、Streamable HTTP 和 Bearer Token 接入方式，列出门店、菜单、商品详情、优惠券、算价等工具。
- 菜单示例 `currentPrice` 为元字符串，算价示例给出整数金额；不能对所有字段采用同一转换规则。字段单位、套餐规格、完整费用需以实际 schema 与账号结果复核。
- 官方营养示例包含能量、蛋白质等，没有糖含量字段；不得据此填零或称任意饮品无糖。

公开示例仅用于设计和契约测试，不能证明账号已连接或产品已可用。

## 方案选择

采用“轻量网页 + 本机 Node 服务 + 现有 Runtime”。不用另写一套前端推荐算法，也不引入 LLM 服务或大型前端框架。网页在同源下调用服务，示例和真实模式复用决策流程。

备选纯静态方案更容易公开访问，但当前领域代码依赖 Node 和文件读取；另写算法会使演示与 Runtime 分叉。云端托管真实账号增加账户隔离和凭据管理范围，本轮不采用。

初版可通过仓库命令启动，无需麦当劳账号或模型 API Key。公开在线演示待初版验收后单独推进；本轮不承诺已经存在在线体验链接。

## 用户流程

1. 进入页面即明确“示例体验”或“真实菜单”；默认是无需账号的示例体验。
2. 输入预算，选择“饮品不含糖”“不吃鸡肉”等有实现依据的限制，点击“帮我选”。结构化控件是唯一条件来源；本轮不假装支持任意自然语言解析。
3. 显示一个首选：具体商品、数量、完整实付、必要费用、用券优惠、为何符合要求，以及数据模式。示例商品名称和金额始终带示例标识。
4. 用户修改条件后，旧结果立即变成待刷新状态；只有最新请求能更新结果。空结果说明已核验候选没有满足条件，不放宽限制。
5. 展开“查看依据”可读到门店、渠道、查询时间、费用明细和饮品证据。技术字段仅放在开发者示例文件，不进入普通用户主流程。

不增加付款按钮、虚构收藏成功、虚构历史或推荐接受次数。演示只使用当前输入，不写长期记忆；偏好模块保留现有 CLI 用法和独立示例。

## 模块和接口

- `runtime/src/web-server.ts`：绑定 `127.0.0.1`，提供网页和有限 JSON API；不暴露通用 MCP 转发接口。
- `runtime/src/web/`：请求校验、服务生命周期、结果投影；独立于页面表达和供应商绑定。
- `runtime/web/`：原生 HTML、CSS、浏览器 JavaScript，无需前端构建工具。
- `runtime/src/providers/official-pickup-profile.ts`：到店自取绑定，按已验证操作逐项启用。未验证映射保持关闭。
- `runtime/src/official-diagnostics.ts`：只读发现和验证，输出脱敏状态，不记录 Token 或原始账号载荷。
- `runtime/examples/`：推荐引擎、偏好仓库、供应商替换的最小可运行例子；不提前拆成多个发布包。

网页 API 为本地应用接口，不改变现有三个 MCP 工具：

| 接口 | 内容 |
| --- | --- |
| `GET /api/status` | 当前数据模式、推荐能力和已绑定门店；无 Token、账号标识、地址、原始错误 |
| `POST /api/recommend` | 有限 JSON：预算分值、避含糖饮品、排除鸡肉；服务将其转成现有结构化意图 |
| 静态资源 | 仅已知网页文件；不按请求路径开放仓库或数据库 |

API 严格验证 JSON、整数金额、布尔值和未知字段；限制请求体和同时运行的请求数量。仅允许同源请求，拒绝跨站 Origin 和非 JSON 写请求；Token 只由启动进程环境提供。服务使用非持久临时状态，不将任意网络请求登记为受信任记忆写入。

真实模式不能失败后静默换成示例模式；模式切换需要重新启动并清空旧结果。浏览器不得接触供应商 Token。公共部署不得沿用含真实 Token 的本地配置。

## 官方绑定与验收

第一阶段只读到店自取：`query-nearby-stores` → 用户选定门店 → `query-meals` → 必要 `query-meal-detail` → 可用优惠券 → `calculate-price`。不创建订单、不领取券、不读取历史、不消耗积分。

启动前由用户在本机配置官方 Token，不通过聊天发送。诊断先取得实际工具 schema；门店必须来自真实查询与用户选择，不使用文档占位编码。即时自取使用经过验证的 `orderType` 与 `beType`；预约、外送、团餐和随单购买会员本轮拒绝。

商品以原始编码为键，默认规格和套餐组成必须经过详情核实。分类、鸡肉标签、无糖饮品证据不能靠模糊名称猜测；未知证据的商品不能通过相关硬限制。营养匹配若不能唯一对应商品和规格，保留未知。

券需保留 `couponId`、`couponCode` 与适用商品的绑定关系。当前领域接口传券 ID，供应商映射负责生成实际工具所需的商品内券字段，不虚构整单券参数。无法确定兼容关系时不使用该券。

报价只在金额单位、商品数量、套餐组成、必付费用、优惠和应付总额均核对通过时成为合格结果。菜单优惠价仅用于候选，不视为最终实付。随单购优惠需要额外付费会员时不自动启用。过期、未知费用、范围不匹配或结构变化均返回无法核验。

上游没有明确锁价期限时，给出短暂的本地刷新期限，并说明它不是供应商锁价。到期后禁用旧结果作为当前已核验价格，可重新查询。金额统一以分整数计算，显示时格式化为元。

绑定状态区分“公开文档研究”“契约测试通过”“真实账号验证通过”。只完成前两项时，README 和页面不得称真实闭环已经打通。

## 视觉设计

页面上部是需求操作区，下部是单份结果；桌面结果偏右，移动端按输入、结果、依据排列。金色双拱门只用于结果的识别元素，内容列表保持开放排版，避免卡片套卡片和三列等宽卡片。没有手机或浏览器假边框。

复用暖中性色、锚色相 85；UI 颜色全部 OKLCH，强调面积不超过约 3%。字体为 Bricolage Grotesque 与 Noto Sans SC，使用 `font-display: swap`。颜色、字体、字号、间距、圆角、层级和动效先进入语义 token，之后仅用 `var(--token)` 引用；样式表顶部写设计戳。

首次结果仅一次 transform / opacity 编排，合计不超过 500ms；reduced-motion 使用 150ms 透明度过渡。焦点环瞬时出现，触屏和键盘均能完成选餐。正文不低于 14px，字号最多五档。

食物素材优先使用真实查询返回的可验证图片；示例页面可用文本和原创拱门构图，不用生成食物冒充真实商品。正文对比度至少 4.5:1，边界与焦点至少 3:1；验证 320、375、414、768、1440 宽度。没有真实用户数据，不展示指标、证言或用户数量。

## 测试和交付标准

- 保留并运行现有 Runtime 测试、类型检查、构建、CLI 演示。
- 新 API 测试：有效预算、非法金额、未知字段、跨站请求、并发限制和服务关闭。
- 配餐测试：无糖限制、鸡肉排除、费用导致超预算、无合格组合；结果与现有引擎一致。
- 数据契约测试：元和分的转换、券与商品映射、套餐默认组成、未知饮品证据、报价范围、缺失费用、随单购优惠、过期报价。
- 浏览器验证：预算和限制可改、错误可恢复、旧响应不覆盖新条件、过期结果标识、键盘操作、窄屏无横向滚动、可点击文案单行、reduced-motion。
- 真实验收需要官方 Token、实际门店和只读查询；没有这些条件时明确交付剩余接入步骤，不制造“通过”记录。
- README 首屏增加实际演示截图与启动命令、准确能力状态；更新 Skill 指引和复用例子，完成验证后同步 GitHub。
