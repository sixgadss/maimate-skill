# 选餐、惊喜与当前会话

## 当前会话状态

在宿主允许的当前会话范围维护：门店与渠道、履约范围、人数和临时餐位、硬预算、各餐位限制、当前草稿、报价引用、已展示组合签名、拒绝原因、探索开关。它不是自动持久记忆。

组合签名由排序后的商品 ID、规格 / 配置 ID、数量构成，合并重复行。换名称、换券、换显示顺序不构成新组合；不同规格或真实数量变化才改变签名。多人比较还需要保留餐位分配。没有稳定商品与规格 ID 时不能保证准确去重，应说明限制。

## 直接点餐

1. 匹配明确商品和合法规格，保留数量与“不加饮料”等负向要求。
2. 若同名对应多个商品或必选规格不明确，只询问会影响实际篮子的那一项。
3. 有精确篮子核价能力时直接核价。推荐工具没有该输入时，不伪造参数、不让推荐结果替代明确商品。
4. 核价能力缺失时列为草稿，指出下一步去官方点餐；不编造跳转链接。

## 代选与老样子

信息足够时给一个首选；用户主动比较时最多三个合格候选。健康或运动场景只依据实际营养证据；赶时间可以减少组合复杂度，但不能据此保证出餐更快。

老样子使用用户选定的真实收藏或适用的已完成历史。只有一笔历史称“上次那份”。每次重新核价，缺货、规格、券及价格变化明确展示。没有历史则说明，并继续帮选，不编造记忆。

## 多人代点

建立本餐临时餐位，不要求建立社交关系或提供同伴姓名。“我不喝有糖，他要普通饮料”是两个不同的饮品约束，不能通过一个全局 avoidSugaryDrinks=false 表达，也不能让全局 true 抹掉同伴明确选择。

共享配餐只对实际食用者应用限制；人数、共享范围或总预算歧义会影响结果时集中澄清。先形成按人分配的草稿，再将整体篮子交给供应商核价。多份单人报价相加不能证明多人实际总价：运费、最低消费、券使用次数和门店规则可能不同。

只有分别报价能力时，可以显示各自草稿与已知事实，但总额与预算合格状态保持未知，直到整体核价。不能将各人偏好混入付款账户的永久画像。账户单人 Runtime 会合并本人的长期偏好，不能用它替具有不同要求的同行者选餐；必须使用可独立表达餐位约束的真实能力，否则只保留同行者需求草稿。

## 受控惊喜

1. 用户主动选择“换口味”“惊喜”时启用探索；保留预算、饮食限制和明确锁定的商品。
2. 用户在当前请求主动给出明确预算时，以该预算为本次探索上限；例如“换一份，三十以内”已经允许选择 29 元，不再追问一次。若同时说“不加钱”，则仍以 min(明确预算, 当前完整实付) 为上限。用户仅说“给点惊喜”而未重述预算时，默认上限为 min(已有硬预算, 基准完整实付)；旧预算尚有余额不意味着自动加价。
3. 没有基准报价时沿用明确硬预算；没有预算可选口味探索，但不能承诺“不加钱”。
4. 在实际返回且验证合格的候选中，排除本次已展示 / 拒绝的签名。工具有受支持的排除参数才传入；没有就本地筛选已返回集合，不虚构参数或无限反复调用。
5. 新旧价格必须同一用户、门店、渠道、履约时点、份量含义和费用口径，且均有效，才能说“同价换”。仅商品小计更低不满足要求。
6. 说明变化：换了哪个主食或配餐，实付是否变化，哪个限制保留。用户接受前保留原稿。
7. 没有合格新候选时直说：当前没找到符合这些条件的另一份。保留原组合或请用户选择调整哪个条件。

不要以拆掉用户要求的餐位、减少明确数量来制造“同价惊喜”。不暗中加购、用积分、抽奖或声称“必中奖”“稀有”。不能排除整个旧篮子里的所有单品来模拟组合去重。

## 示例（均为合成数据）

当前 A 完整实付 28 元，历史硬预算 30 元，A 已展示；B 不同组合 29 元，C 小计 27 元但运费未知。用户仅说“给点惊喜”时保持 28 元实付边界，不能直接给 B，也不能称 C 符合预算。用户当前说“给点惊喜，三十以内”时可提出完整报价仍有效的 B，不重复询问预算授权。用户说“三十以内，但不加钱”时仍以 28 元为上限。

## 修改与结束

更换商品、配置、数量、门店、渠道、时间或地址后清除报价有效状态并重新核验。用户说“就它”只是选定草稿；按实际交易能力继续，不能把接受反馈当订单完成。

餐后评价是独立信号。口味、份量与服务反馈分开处理；模糊的“不满意”不能自动永久排除全部商品。用户不想被问就结束，不追加例行问卷。
